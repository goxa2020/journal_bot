- Ветка `main`, рабочее дерево чистое. Последние коммиты: документация, `fix(auth)`, `build: ...`, `fix(tooling): ...`.
- Docker-стек поднят (бот, Postgres, pgbouncer, Redis, админка, Prometheus, Grafana). Бот работает.
- VPN на хосте работает как локальный прокси `127.0.0.1:10809`; в `.env` для контейнера
  `TELEGRAM_PROXY=http://host.docker.internal:10809`, в `.env.local` — `127.0.0.1:10809`.
- `.env.local` — локальный запуск: `DB 127.0.0.1:6432`, `Redis 127.0.0.1:6380`.
- **Один токен бота = один поллер.** Перед локальным запуском: `docker compose stop bot`;
  после: `docker compose up -d bot`. Два поллера одновременно дадут `409 Conflict`.
- Docker и pre-commit требуют полного доступа к ФС (sandbox escalation), иначе будут
  `access denied` / `readonly database` — это ограничение песочницы, а не прав Windows.
- Тесты и проверки: `just pre`, `just mypy`, `uv run pytest`, `just dev`, `just watch`.
- Локальные `.mo` для i18n не в git: после правки `.po` обязательно `just babel-compile`.

## Задачи Фазы 0 (в этом порядке)

### 0.2. Обязательный `ENCRYPTION_KEY` и валидация на старте (остаток задачи)

Сейчас `bot/core/config.py` при отсутствии ключа генерирует случайный — после рестарта
сохранённые пароли перестают расшифровываться.

- Сделай `ENCRYPTION_KEY` обязательным полем `Settings` (без дефолта) и валидируй его
  (`Fernet(key)`), при ошибке — понятное сообщение: что это за ключ и как сгенерировать.
- Убери `Fernet.generate_key()` из конфига.
- Вынеси шифрование в `bot/core/encryption.py`: `encrypt(text) -> str`, `decrypt(token) -> str | None`,
  `validate_key()`. `bot/services/users.py` использует его; поведение при `InvalidToken` — по-прежнему
  «вернуть None и залогировать warning».
- Проверь, что `.env` и `.env.local` содержат валидные ключи (не печатай их), и что контейнер
  и локальный запуск стартуют.

**Критерий:** без переменной окружения старт падает с понятным текстом (не трейсбек на 100 строк);
с ключом — работает; unit-тест: roundtrip, невалидный ключ, повреждённый токен.

### 0.3. Кеширование в `bot/services/users.py`

Проверь фактическое состояние (формулировка в ROADMAP может быть неточной — если так, поправь её):

- `is_authorized` вызывается на каждом апдейте и каждый раз ходит в БД — оберни `@cached`
  с ключом от `user_id`; сброс уже вызывается в `set_user_data`.
- Проверь, что `clear_cache(...)` строит тот же ключ, что `@cached`, и реально сбрасывает
  (`set_language_code`, `set_edu_credentials`, `set_user_data`).
- `get_all_users` и `get_admins_ids` кешируются Pickle-сериализатором с ORM-объектами —
  это хрупко (detached-инстансы, стухший список админов). Либо кешируй только id,
  либо отключи кеш у этих функций; решение объясни комментарием.
- TTL оставь осмысленным (10 с для горячих проверок допустимо).

**Критерий:** unit-тест с `fakeredis` и стабом сессии: второй вызов не идёт в БД,
после `set_*` кеш сброшен.

- Секреты: не печатать значения из `.env`/`.env.local`, не коммитить их.
- Коммиты — Conventional Commits, один коммит на задачу или логическую пару
  (`fix(config): require ENCRYPTION_KEY`, `test: add pytest scaffolding` и т.п.).
  Хуки работают через `.githooks`; **не** использовать `--no-verify`. Если хук упал —
  разобраться, а не обходить.
- Не запускать бота одновременно в контейнере и локально.
