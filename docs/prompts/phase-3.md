- **Прод живёт на сервере** `192.168.1.7` (`/srv/journal_bot`, Debian 13, ключ

- **Один токен = один поллер.** Нельзя запускать второго бота одновременно с продовым —
  Telegram вернёт `409 Conflict`. Для локальной проверки: останови прод-бота

  локально и верни обратно. Второй экземпляр не поднимай.
- **Telegram с сервера идёт через xray** (`xray.service`, HTTP-прокси `172.17.0.1:10809`,
  `TELEGRAM_PROXY=http://host.docker.internal:10809` в серверном `.env`). Локально на Windows
  Telegram доступен через VPN-прокси `127.0.0.1:10809`:
  - для `uv add/lock/sync` нужен `$env:HTTPS_PROXY='http://127.0.0.1:10809'`;
  - при сборке с новыми зависимостями — build-args с `host.docker.internal:10809`;
  - edu-tpi с сервера доступен напрямую, прокси ему не нужен.
- **Серверный DNS — публичный** (`1.1.1.1`/`8.8.8.8` в `daemon.json` и `dhcpcd.conf`):
  роутер отдавал NXDOMAIN/NODATA, из-за этого контейнеры не резолвили edu-tpi. Не «возвращай
  как было».
- **Сборка на сервере может падать на `ghcr.io`** (`lookup ghcr.io ... no such host`), хотя
  системный `getent` резолвит. Проверенный обход: собрать образ на машине разработчика,
  `docker save` → gzip → `scp` → `docker load` → `docker compose ... up -d --no-build`.
  Не путай вложенный tar: `docker save` уже создаёт tar, его нужно именно gzip-нуть, а не
  заворачивать в ещё один tar. Альтернатива — починить `deploy.ps1` и задокументировать.
- **БД и миграции.** Голова — `2026_11_21_grades_v2`. Для фазы 3 миграции не нужны: все поля
  настроек уже есть. Если всё-таки понадобится менять схему — остановись и спроси

- Если `uv run` падает на доступе к `%LOCALAPPDATA%\uv`, используй
  `.venv\Scripts\python.exe -m pytest`, `.venv\Scripts\ruff.exe`, `.venv\Scripts\mypy.exe`.

## Решения для фазы 3 (следуй им)

1. **Источник данных для уведомлений.** Расширь `JournalSyncResult` и `SyncSummary` так,
   чтобы после дифа были доступны новые уроки с названием журнала, датой, парой, значением и
   флагами. Удобный вариант — dataclass `NewGradeNotice` в `bot/services/grade_sync.py`:
   `journal_id`, `journal_name`, `journal_type`, `date`, `hour_number`, `value`,
   `number_value`, `is_mark`, `is_pass`, `lesson_key`. В `SyncSummary` — список `new_notices`.
   `SyncSummary.as_dict()` остаётся JSON-безопасным (в Celery-result уходят только числа и
   строки; dataclass/date туда не класть).
2. **Кто и когда отправляет.**
   - `sync_user_manual`: пользователь сам нажал «Обновить» и ждёт ответ. Если есть новые
     оценки и уведомления включены — отправь **одно** сообщение с новыми оценками вместо
     счётчика «новых N»; если новых нет — существующая сводка «Изменений нет» (или
     «обновлено N»). Не отправляй сводку и уведомление двумя сообщениями.
   - `sync_user_after_login`: первичный импорт, уведомления **не отправляются**.
   - Для будущей фоновой синхронизации (фаза 4) оставь публичный метод
     `NotificationService.notify_new_grades(user_id, notices)` (или аналогичный), который
     сможет вызвать `sync_all_users`. Не реализуй сам `sync_all_users` — это фаза 4.
3. **День/ночь.** Ночь — 22:00–07:59 Europe/Moscow. Если `morning_notification_enabled` и
   сейчас ночь, новые оценки складываются в Redis и уходят утром; иначе — сразу. Время утра
   берётся из `users.morning_notification_time` (по умолчанию 08:00). Если утро уже прошло —
   следующий день. При ручной синхронизации ночью пользователь получает короткий ответ
   «синхронизировано, новые оценки придут утром», а не тишину.
4. **Одно сообщение — один батч.** Не отправляй по сообщению на каждую оценку. В дневном
   уведомлении — список всех новых оценок из одной синхронизации; в ночном — один список
   утром.
5. **Дедупликация.** Ключ `notify:sent:{user_id}:{lesson_key}` (TTL 7 дней), где
   `lesson_key = f"{journal_id}:{date.isoformat()}:{hour_number}"`. Маркер ставится до
   отправки/постановки в ночную очередь; повторная синхронизация ту же оценку не уведомляет.
   Если отправка не удалась — маркеры этих оценок нужно снять, чтобы повтор мог отправить.
   Для ночной очереди дополнительно защити постановку одного `send_night_batch` на
   пользователя (`notify:night:scheduled:{user_id}`, NX, TTL до утра).
6. **Настройки.** `/settings` и callback `settings` из меню: включить/выключить уведомления,
   включить/выключить накопление ночью, выбрать время утра. Время — пресеты
   `07:00`, `08:00`, `09:00`, `10:00` по кругу (проще и тестируемее FSM-ввода). Экран живёт
   в одном сообщении (`edit_message_text`), кнопка «Главное меню» возвращает в меню.
   Неавторизованному — приглашение войти.
7. **Ошибки Telegram.**
   - `TelegramForbiddenError` (бот заблокирован) → `notification_enabled=False` в БД, лог,
     без бесконечных повторов.
   - `TelegramRetryAfter` → подождать `retry_after` (с разумным потолком, например 60 с) и
     повторить один раз; если снова не вышло — `RetryableError`.
   - Прочие сетевые ошибки → `RetryableError` (задача повторится), маркеры дедупликации
     снять.
8. **Метрики.** `notifications_total` (Counter, labels `kind=immediate|night`,
   `status=sent|skipped|failed|blocked`) и `sync_new_grades` (Counter, labels
   `type=manual|auto`). Метрики живут в процессе воркера; HTTP-экспорт — фаза 8, не тащи
   celery-exporter сюда. Для аналитики добавь worker-safe helper (без `Message`/`CallbackQuery`)
   и событие `New Grade`/`Sync New Grades`, но не роняй отправку, если провайдер не настроен
   или упал.

## Задачи Фазы 3 (в этом порядке)

### 3.1. `NotificationService`: немедленное уведомление

- `bot/services/notifications.py`: сервис, который по пользователю и списку `NewGradeNotice`
  проверяет настройки, дедупликацию и время, решает «отправить сейчас / в ночную очередь /
  ничего» и формирует данные для сообщения. Сервис не должен импортировать
  `bot.core.loader` и не должен сам создавать `Bot`: отправка — в задачах.
- `bot/services/users.py`: worker-safe функции чтения и записи настроек без `@cached`
  (по аналогии с `load_edu_credentials`): `load_notification_settings`,
  `set_notification_enabled`, `set_morning_notification` (включено + время).
- Формат текста — в `bot/utils/formatters.py` или в сервисе, но с gettext-ключами:
  `📊 Новые оценки`, строки `ДД.ММ.ГГГГ — предмет (Л/П) — значение`, без лишней легенды.
  Экранируй HTML в названиях журналов.
- В `sync_user_manual` встрой одну ветку: новые оценки → уведомление вместо счётчика,
  без новых → прежняя сводка. В `sync_user_after_login` не уведомляй.

**Критерий:** днём одна новая оценка → одно сообщение; несколько новых → одно сообщение
списком; `notification_enabled=False` → сообщения нет; повторный вызов с тем же
`lesson_key` → сообщения нет.

### 3.2. Ночное накопление и `send_night_batch`

- `bot/tasks/notify.py`: `send_grade_notification(user_id, lesson_keys)` и
  `send_night_batch(user_id)`; маршрут `bot.tasks.notify.*` → очередь `notify` уже настроен,
  не дублируй `task_routes`. Добавь `bot.tasks.notify` в `include` Celery-приложения.
- Ночная очередь: `RPUSH notifications:night:{user_id}` (JSON-записи), `EXPIRE` до утра
  (утро + 2 часа). `send_night_batch` читает и очищает список, отправляет один список,
  повторы/ошибки обрабатывает по 3.4.
- `send_night_batch.apply_async(eta=...)` с timezone-aware временем Europe/Moscow; не
  создавай второй `send_night_batch` при повторной синхронизации
  (`notify:night:scheduled:{user_id}` NX).
- Учти `task_acks_late=True`: повторный запуск ночной задачи не должен отправлять тот же
  список дважды (дедупликация + очистка ключа).

**Критерий:** оценка в 23:00 при включённом накоплении не отправляется сразу; `send_night_batch`
в 08:00 отправляет один список и очищает ключ; при выключенном накоплении — сразу; повторная
задача не дублирует.

### 3.3. Экран `/settings`

- `bot/handlers/message/settings.py`, `bot/handlers/callback/settings.py`,
  `bot/keyboards/inline/settings.py`: команда `/settings` и callback `settings` из меню.
- Кнопки: «🔔 Уведомления: вкл/выкл», «🌙 Копить ночью: вкл/выкл», «⏰ Утро: HH:MM»,
  «🏠 Главное меню». Время циклически меняется по пресетам.
- Экран только из БД, без сети; одно сообщение на диалог; после изменения — обновить текст

- Неавторизованный пользователь получает приглашение войти.

**Критерий:** тесты: переключение флага пишет в БД; время меняется по кругу; «Главное меню»
возвращает меню; неавторизованный не меняет настройки.

### 3.4. Дедупликация и ошибки Telegram

- Реализуй маркеры `notify:sent:*` и их снятие при неудаче.
- Классифицируй `TelegramForbiddenError` и `TelegramRetryAfter` (см. решения выше).
- При блокировке бота `notification_enabled=False`, но очередь и другие пользователи не
  ломаются.
- В логах — только `user_id`, `kind`, `status`, без текста оценок и названий журналов
  (названия не ПДн, но лучше не раздувать лог).

**Критерий:** повторный запуск задачи не отправляет второй раз; `TelegramForbiddenError`
выключает уведомления; `TelegramRetryAfter` приводит к одному повтору; ошибка одного
