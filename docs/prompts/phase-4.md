## Решения для фазы 4 (следуй им)

1. **Где живёт групповая синхронизация.** Новый сервис `bot/services/group_sync.py` с
   `GroupSyncService`; задача `sync_all_users` — в `bot/tasks/sync.py`. Логику дифа одного
   журнала вынеси из `GradeSyncService._sync_journal` в метод вида
   `apply_payload(user, brief, payload) -> JournalSyncResult`, который используют и
   `sync_user`, и групповая синхронизация. Дублировать диф нельзя.
2. **Кого синхронизировать.** В `bot/services/users.py` добавь worker-safe (без `@cached`)
   выборку `load_sync_candidates(session)`: `is_authenticated=True`, `group_id` и
   `edu_user_id` не NULL, отсортировано по `group_id`, `id`. Верни dataclass-ы
   (`UserSyncInfo` или `GroupMember`), не ORM-объекты. Пользователей без группы/edu id
   пропускай и считай `skipped`.
3. **Алгоритм группы (ARCHITECTURE §7.3).**
   - `unprocessed` — члены группы по `edu_user_id`.
   - Возьми любого (детерминированно — минимальный `edu_user_id`), получи его токен и
     `list_journals` **один раз на группу** (текущий семестр, как в `GradeSyncService`).
     Если первый токен не дал список (ошибка авторизации), попробуй следующего участника.
   - Для каждого журнала: `JournalCache.get_journal(...)` этим токеном — один HTTP-запрос на
     группу/подгруппу, дальше кеш.
   - Для каждого члена из `unprocessed`, который есть в `payload.student_ids`: примени диф,
     `upsert` и `student_journal`, закоммить транзакцию журнала, запиши `sync_logs` с
     `SyncType.AUTO`, собери `new_notices`, удали из `unprocessed`.
   - Удали из `unprocessed` всех студентов, пришедших в `payload` (их подгруппа обработана),
     даже если это не пользователи бота.
   - `EduEmptyJournalError` по журналу — пропуск (чужая подгруппа), не ошибка.
     `EduAuthError` одного члена — он `failed`, остальные продолжают; `ParseError` журнала —
     ошибка журнала, остальные журналы продолжают; `EduUnavailableError`/`EduRateLimitError`
     — ошибка группы/прогона, не роняй весь прогон.
   - Если за полный проход `unprocessed` не уменьшился — залогируй warning, оставшихся
     пометь failed и выйди из группы (защита от бесконечного цикла).
   - Если список журналов не удалось получить ни для одной группы (edu-tpi лежит целиком),
     брось `RetryableError`: Celery повторит батч, он идемпотентен. Частичные ошибки
     (один журнал/один пользователь) повода для ретрая не дают.
   - Один `EduTpiClient`, один `JournalCache`, одна сессия и один Redis на весь прогон
     `sync_all_users`; `TokenService` — на каждого члена. Список журналов берётся один на
     группу: если у участников он объективно разный, это осознанное упрощение — запиши
     наблюдение в отчёт, но не ходи за списком к каждому.
4. **Уведомления из групповой синхронизации.** После коммита журнала для каждого
   пользователя с новыми оценками вызови
   `send_grade_notification.delay(user_id, [notice.to_dict() …])`. Не отправляй сводки,
   счётчики и «синхронизация завершена» — фоновая синхронизация молчит, кроме новых оценок.
   Ошибку постановки в брокер логируй и продолжай: оценки уже сохранены. Дедупликация внутри
   `send_grade_notification` не даст дублей при повторном прогоне.
5. **Блокировки и границы прогона.**
   - Батч-лок `sync:all:lock` через `task_lock(..., ttl=3600)`: не взяли — верни
     `{"status": "skipped", "reason": "locked"}` без ошибки.
   - Перед дифом каждого пользователя бери `sync:lock:{user_id}` (TTL 120–300 с) и
     **освобождай его после обработки пользователя** (добавь в `bot/tasks/base.py`
     необязательный `release=True` для `task_lock` или отдельный контекст): иначе ручная
     синхронизация этого пользователя будет пропускаться до истечения TTL. Если лок занят —
     идёт ручная синхронизация: пропусти пользователя, посчитай `skipped`, повторный прогон
     подхватит его.
   - Задаче задай `expires=3600`, `soft_time_limit=1800`, `time_limit=1900`: глобальные
     300/250 с рассчитаны на одного пользователя и для батча малы. Глобальные лимиты
     `CelerySettings` не меняй.
6. **Расписание beat (4.3).** В `bot/celery_app.py`:
   ```python
   "sync-all-users": {
       "task": "bot.tasks.sync.sync_all_users",
       "schedule": crontab(minute=0, hour="*/6"),
       "options": {"expires": 3600},
   }
   ```
   Это 00, 06, 12, 18 МСК. «Ночное окно» из ROADMAP — это прогоны 00:00 и 06:00; отдельного
   флага/ветвления не заводи. Маршрут: в `bot/celery_config.py` добавь **точное** правило
   `"bot.tasks.sync.sync_all_users": {"queue": QUEUE_MAINTENANCE}` **до** wildcard
   `"bot.tasks.sync.*"` (порядок ключей в `TASK_ROUTES` важен): батч не должен занимать
   очередь `sync`, где ждут пользователи.
7. **Оппортунистическая синхронизация (4.2).** Новый флаг `SYNC_OPPORTUNISTIC: bool = False`
   в `Settings` и `.env.example`. Когда он включён, **ручная** синхронизация после диффа
   текущего пользователя обновляет ещё и других пользователей бота той же группы, которые
   есть в этом же `payload` (один запрос уже сделан). Уведомляй их через
   `send_grade_notification.delay`. **Не** уведомляй тех, у кого по этому журналу ещё нет
   ни одной оценки в БД (первичный импорт молчит — иначе будет залп «новых» оценок); данные
   им всё равно сохрани. Для `sync_user_after_login` оппортунистическую часть не включай.
   Не трогай пользователей с занятым `sync:lock`. Флаг по умолчанию выключен: он повышает
   риск ложных уведомлений, это осознанный компромисс (ARCHITECTURE §7.3).
8. **Метрики и алерт (4.4).**
   - В `bot/core/metrics.py`: `sync_batch_users` (Counter, label `status=success|failed|skipped`),
     `sync_batch_duration_seconds` (Histogram). Плюс существующий
     `sync_new_grades{type=auto}` по числу новых оценок батча.
   - В `Settings`: `SYNC_ALERT_FAILURE_RATIO: float = 0.2` и
     `SYNC_ALERT_MIN_USERS: int = 5`; добавь их в `.env.example` с комментариями.
   - Если пользователей в прогоне ≥ `SYNC_ALERT_MIN_USERS` и доля `failed` ≥
     `SYNC_ALERT_FAILURE_RATIO`, отправь **одно** сообщение всем админам через

9. **Идемпотентность.** `task_acks_late=True`: повторный прогон не должен создавать дубликаты

### 4.1. `sync_all_users`: группы и подгруппы

- `bot/services/users.py`: `load_sync_candidates`, `load_group_members` (для 4.2),
  `load_admin_ids` (для 4.4) — без кеша, только dataclass-ы/примитивы.
- `bot/services/grade_sync.py`: вынеси диф одного журнала в `apply_payload`; `sync_user`
  должен использовать его же.
- `bot/services/group_sync.py`: `GroupSyncService` с `sync_all()`; результат — dataclass
  `BatchSummary` с числами и `as_dict()`.
- `bot/tasks/sync.py`: `sync_all_users` — батч-лок, прогон, метрики, алерт, JSON-результат.
- Критерий: пустая БД/нет кандидатов — успех с нулями; один пользователь — те же оценки,
  что при ручной синхронизации; два пользователя одной группы — **один** запрос на журнал,
  оба получают оценки и по одному уведомлению; две подгруппы — по одному запросу на
  подгруппу; ошибка авторизации одного не останавливает остальных; повторный прогон не
  создаёт оценок-дублей.

### 4.2. Оппортунистическая синхронизация

- Флаг `SYNC_OPPORTUNISTIC` (см. решение 7), включается только для `sync_user_manual`.
- После диффа текущего пользователя обнови других участников группы из того же `payload`;
  уведомляй только тех, у кого по журналу уже были оценки.
- Критерий: при выключенном флаге чужие оценки не меняются и уведомлений нет; при включённом
  — оценки других участников обновляются, уведомление уходит (день) или ставится в ночную
  очередь (ночь), дублей при повторном прогоне нет; первичный импорт (`after_login`) флаг не
  применяет.

### 4.3. Расписание beat и пересекающиеся запуски

- `beat_schedule` с `sync_all_users` каждые 6 часов (`crontab(minute=0, hour="*/6")`),
  `options={"expires": 3600}`; точный маршрут в `maintenance` до wildcard.
- Батч-лок `sync:all:lock` (TTL 3600), per-user lock, `expires`/`time_limit` задачи.
- Критерий: маршрут `bot.tasks.sync.sync_all_users` → `maintenance`; в `beat_schedule` ровно
  одна запись с нужным расписанием; занятый батч-лок даёт `skipped: locked` без ошибки;
  повторный ручной запуск во время батча не идёт параллельно.

### 4.4. Метрики и алерт

- `sync_batch_users{status}`, `sync_batch_duration_seconds`, `sync_new_grades{type=auto}`.
- Алерт админам по порогу (решение 8), `load_admin_ids` без кеша, gettext-ключ.
- Критерий: тесты через `prometheus_client.REGISTRY` проверяют инкременты; алерт отправляется
  один раз при превышении порога и не отправляется ниже порога; падение Telegram при алерте
  не роняет батч.

### 4.5. Тест «два пользователя одной группы — один запрос на журнал»

- `tests/integration/test_group_sync.py`: фейковый клиент считает `get_journal`; два
  пользователя одной группы, один журнал → ровно 1 запрос; обе строки оценок в БД; по одному
  уведомлению; вариант с подгруппами → 1 запрос на подгруппу; пустой журнал чужой подгруппы
  не считается ошибкой.
- Критерий: тест ловит регрессию, если групповая синхронизация начнёт ходить в edu-tpi за
  каждого пользователя; старые 219 тестов не сломаны.

## Ограничения

- **Только фаза 4.** Не писать `sync_watch_mode_users`, режим ожидания, статистику, экспорт,
  дайджест, Flower/celery-exporter. В `beat_schedule` — только `sync_all_users`.
- **Схему БД не менять.** Все нужные поля есть; если понадобилась миграция — стоп и вопрос
  пользователю.
- Не переиспользовать в задачах глобальные `engine`, `sessionmaker`, `redis_client`, `Bot`.
- `task_acks_late=True` — все задачи идемпотентны; дедупликация уведомлений обязательна.
- Уведомления из батча — только `send_grade_notification.delay`, без сводок и счётчиков.
- i18n: новые пользовательские строки и текст алерта — через `_()`/`n_()`, обе локали (`ru`,
  `en`), затем `pybabel compile` (`just babel-compile`); `.mo` в git не попадают.
- Секреты: не печатать `.env`/`.env.local`; в логах — только id и числа.
- Коммиты — Conventional Commits, один коммит на задачу или логическую пару.
  Хуки через `.githooks`; `--no-verify` не использовать.
- **Прод не ломать.** Миграций нет; перед деплоем — свежий бэкап, после — healthy.
  Если серверная сборка падает на `ghcr.io` — `sudo docker pull` базового образа, затем
  `deploy.ps1`, либо доставка готового образа.
