## Введение

### Назначение системы

Telegram-бот для студентов Политехнического института ДГТУ, предоставляющий быстрый доступ к электронному журналу успеваемости edu-tpi.donstu.ru.

### Ключевое преимущество

**Агрегированный вывод:** Пользователь получает информацию по **всем своим журналам сразу**, в отличие от сайта, где приходится открывать каждый журнал отдельно.

### Технологический стек

- **Backend:** Python 3.10+, aiogram (async Telegram Bot API)
- **База данных:** PostgreSQL 15+ (основное хранилище)
- **Кеширование:** Redis 7+ (токены, групповые журналы, справочники)
- **Очередь задач:** Celery 5+ с Redis broker
- **Инфраструктура:** Docker, Docker Compose
- **Мониторинг:** Prometheus, Grafana, Sentry, Flower (Celery UI)
- **Админ-панель:** Flask-Admin

### Принципы проектирования

1. **Асинхронность повсюду** - все IO операции неблокирующие
2. **Неблокирующая обработка** - бот ВСЕГДА отвечает мгновенно, тяжёлые операции в Celery
3. **Групповое кеширование** - минимизация запросов к внешнему API
4. **Агрегированный вывод** - вся информация пользователю сразу
5. **Оппортунистическая синхронизация** - обновление данных всех студентов из полученного журнала
6. **Минимализм хранения** - сохраняем только необходимое
7. **Приоритизация задач** - ручные операции выполняются первыми

## Спецификация edu-tpi API

### Базовые параметры

```
Base URL: https://edu-tpi.donstu.ru/api
Аутентификация: Bearer Token (JWT)
Формат: JSON
Кодировка: UTF-8
```

### 1. Получение Fingerprint

**Эндпоинт:** `GET /UserInfo/Devices/RandomIdentity`

**Назначение:** Получение уникального идентификатора устройства для авторизации

**Ответ:**
```json
{
  "data": {
    "randomIdentity": "long-random-string..."
  },
  "state": 1,
  "msg": "",
  "time": 12.0
}
```

**Использование:** Обязательный параметр для авторизации

---

### 2. Авторизация

**Эндпоинт:** `POST /tokenauth`

**Тело запроса:**
```json
{
  "userName": "email@example.com",
  "password": "password",
  "fingerprint": "randomIdentity_from_step_1"
}
```

**Ответ:**
```json
{
  "data": {
    "userName": "Максимов Г.К.",
    "accessToken": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
    "expiresIn": 10080.0,
    "id": -22069
  },
  "state": 1
}
```

**Важно:**
- `expiresIn` в минутах (10080 = 7 дней)
- `accessToken` используется в заголовке `Authorization: Bearer {token}`

---

### 3. Валидация токена и получение информации о пользователе

**Эндпоинт:** `GET /tokenauth`

**Заголовки:** `Authorization: Bearer {accessToken}`

**Ответ:**
```json
{
  "state": 1,
  "data": {
    "userName": "goxa1@vk.com",
    "user": {
      "userID": -22069,
      "groupID": 3273,
      "group": "584 ис-3",
      "fio": "Максимов Г.К.",
      "fullName": "Максимов Георгий Константинович"
    }
  }
}
```

**Использование:**
- Проверка валидности токена
- Получение `groupID` для группового кеширования
- Получение краткой формы ФИО (`fio`)

---

### 4. Список журналов

**Эндпоинт:** `GET /Journals/JournalList`

**Заголовки:** `Authorization: Bearer {accessToken}`

**Ключевые поля ответа:**
```json
{
  "data": {
    "returnList": [
      {
        "id": 27919,
        "groupName": "584 ис-3",
        "dis": "Название дисциплины",
        "type": "Лек/Пр/Лаб",
        "year": "2025-2026",
        "prepodName": "Иванов И.И.",
        "dateCount": 16,
        "maxDateCount": 26.0,
        "passes": 0
      }
    ],
    "fillingProcent": 67
  }
}
```

**Что используем:**
- `id` - идентификатор журнала для детального запроса
- `dis` - название дисциплины
- `type` - тип занятий
- `prepodName` - преподаватель

**Что НЕ используем:**
- `dateCount`, `maxDateCount` - вычисляются из БД
- `passes` - вычисляется из оценок
- `fillingProcent` - не критично

## Стратегия хранения данных

### 1. PostgreSQL - Постоянное хранилище

#### Таблица `users`

**Назначение:** Учётные записи пользователей бота

**Поля:**
- `id` - ID пользователя в Telegram (primary key, unique, indexed)
- `language_code`
- `edu_login_encrypted` - зашифрованный логин edu-tpi
- `edu_password_encrypted` - зашифрованный пароль edu-tpi
- `edu_user_id` - ID студента в системе edu-tpi (indexed)
- `group_id` - ID группы (indexed)
- `group_name` - название группы ("584 ис-3")
- `full_name` - краткая форма ФИО ("Максимов Г.К.")
- `is_authenticated` - флаг успешной авторизации
- `notification_enabled` - включены ли уведомления
- `morning_notification_enabled` - откладывать ночные уведомления до утра (default: true)
- `morning_notification_time` - time время начала утра для уведомлений (default: 08:00)
- `watch_mode_expires_at` - timestamp окончания режима ожидания оценок (NULL = выключен) 
- `watch_mode_last_sync_at` - timestamp последней синхронизации в режиме ожидания
- `created_at`, `updated_at` - timestamps

**Индексы:**
- `idx_telegram_id` - быстрый поиск по Telegram ID
- `idx_group_edu_user` - поиск по группе и edu_user_id
- `idx_group_id` - группировка пользователей по группам

---

#### Таблица `journals`

**Назначение:** Журналы

**Поля:**
- `id` - ID журнала в edu-tpi (primary key, unique, indexed)
- `name` - название дисциплины
- `teacher_name` - ФИО преподавателя
- `type` - тип занятий (Лек/Пр/Лаб)
- `created_at`, `updated_at`

**Обновление:** Редко (при первом появлении журнала)

---

#### Таблица `grades`

**Назначение:** Оценки и посещаемость студентов

**Поля:**
- `id` - ID занятия из edu-tpi (dateID) (primary key)
- `user_id` - ссылка на users (indexed)
- `subject_id` - ссылка на subjects (indexed)
- `date` - дата занятия (тип: DATE PostgreSQL, формат хранения: YYYY-MM-DD)
- `value` - отображаемое значение ("1"-"5", "Н", "У", "Б", "О", "") из journalVal.value
- `number_value` - числовое значение **только для оценок 1-5** (1.0-5.0), NULL для остальных
- `is_mark` - флаг оценки (true только для 1-5)
- `is_pass` - флаг пропуска (true для Н, О)
- `is_valid_pass` - флаг уважительной причины (true для У, Б)
- `created_at`, `updated_at`

**Индексы:**
- `idx_user_lesson` - быстрый поиск оценок пользователя
- `idx_user_subject_date` - фильтрация по предмету и дате
- `uq_user_lesson_subject` - уникальность записи

**Примечание:**
- Система оценок **пятибалльная** (1, 2, 3, 4, 5)
- Поля `is_mark`, `is_pass`, `is_valid_pass` копируются из journalVal

---

#### Таблица `sync_logs`

**Назначение:** Логи синхронизаций

**Поля:**
- `id`, `user_id`, `sync_type` (manual/auto/watch_mode)
- `status` (success/error/partial)
- `new_grades_count`, `updated_grades_count`
- `message`
- `created_at`

---

#### Долгосрочные справочники (TTL: 30 дней)

**Легенда журнала:**

```

```

**Обновление:** При первом запросе или вручную раз в месяц

```

### 3. Что НЕ хранится

**Вычисляется на лету:**
- Статистика (средний балл, процент посещаемости)

- Процент заполнения журнала

- Права редактирования (allowEdit)

- Детали расписания (rasp)

## Модульная архитектура

### 1. Модуль авторизации (`AuthService`)

**Ответственность:** Управление аутентификацией и сессиями

**Ключевые операции:**

**1.1 Получение fingerprint**
- Запрос к `/UserInfo/Devices/RandomIdentity`
- Возврат `randomIdentity` для использования в авторизации

**1.2 Авторизация пользователя**
- Получение fingerprint
- Отправка учётных данных + fingerprint на `/tokenauth`
- Получение `accessToken`, `expiresIn`, `id`
- Запрос информации о пользователе через `GET /tokenauth`
- Извлечение `groupID`, `fio` (краткая форма ФИО)

**1.3 Хранение учётных данных**
- Шифрование данных через Fernet
- Сохранение в БД: `edu_username_encrypted`, `edu_password_encrypted`, `edu_user_id`, `group_id`, `group_name`, `full_name`
- Установка флага `is_authenticated = True`

**1.4 Управление токенами**
- Проверка кеша Redis перед запросом нового токена
- Автоматическое обновление при истечении срока
- Кеширование с TTL = 30 минут

**1.5 Валидация токена**
- Запрос `GET /tokenauth` для проверки валидности
- Обновление информации пользователя при необходимости

**Взаимодействие:**
- **Входящие:** Handlers, Celery Workers
- **Исходящие:** edu-tpi API, Database (User), Redis (токены), Encryption service

---

### 2. Модуль парсинга журналов (`JournalParser`)

**Ответственность:** Взаимодействие с edu-tpi API и парсинг данных

**Ключевые операции:**

**2.1 Получение списка журналов**
- Запрос `GET /Journals/JournalList` с токеном
- Извлечение базовой информации о дисциплинах

**2.2 Получение детальной информации журнала**
- Запрос `GET /Journals/Journal/{journalId}`
- Получение `journalData` (оценки ВСЕХ студентов), `journalDates`, `journalVal`
- Извлечение флага `isSubGroup`

**2.3 Парсинг справочника значений оценок**
- Преобразование массива `journalVal` в словарь `{id: GradeInfo}`
- Определение типов значений (оценка/посещаемость/спецзначение)

**2.4 Парсинг оценок всех студентов**
- Итерация по `journalData`
- Для каждого студента:
  - Извлечение ID студента из поля `id`
  - Поиск всех полей-оценок (числовые ключи типа "346734")
  - Сопоставление с датами из `journalDates`
  - Преобразование ID значения в фактическое значение через `journalVal`
- Возврат структуры `{student_id: [GradeData, ...]}`

**2.5 Извлечение оценок конкретного студента**
- Поиск студента по `edu_user_id` в распарсенных данных
- Возврат массива оценок студента

**Взаимодействие:**
- **Входящие:** Celery Workers
- **Исходящие:** edu-tpi API, Redis (кеш журналов), Sentry (логирование ошибок)

---

### 3. Модуль синхронизации (`GradeSyncService`)

**Ответственность:** Координация процесса синхронизации

**Ключевые операции:**

**3.1 Координация синхронизации пользователя**

**Процесс:**
1. Получение токена через `AuthService`
2. Запрос списка журналов через `JournalParser`
3. Для каждого журнала:
   - Проверка кеша (с учётом подгрупп)
   - Если кеша нет или студент не найден:
     - Запрос детального журнала
     - Парсинг оценок ВСЕХ студентов
     - Кеширование для группы/подгруппы
   - Извлечение оценок конкретного студента
4. Обнаружение новых оценок (сравнение с БД)
5. Сохранение новых оценок в БД
6. **Оппортунистическая синхронизация:** Для всех найденных новых оценок других студентов из журнала:
   - Проверка: зарегистрирован ли студент в боте?
   - Если ДА → сохранение оценок в БД
   - Если ДА → отправка уведомления студенту
7. Запись лога синхронизации

**3.2 Координация массовой синхронизации всех пользователей**

**Процесс:**
1. Получение всех активных пользователей из БД
2. Группировка пользователей по `group_id`
3. Для каждой группы:
- 3.1. Инициализация множества необработанных студентов
	- `unprocessed_students = {edu_user_id всех пользователей группы}`
- 3.2. Итеративная обработка подгрупп (пока `unprocessed_students` не пусто):
	- Выбор первого необработанного студента
	- Получение токена этого студента
	- Запрос журнала токеном студента
	- Парсинг оценок всех студентов из ответа
	- Определение ключа кеша (с учётом `isSubGroup`)
	- Кеширование для группы/подгруппы
	- Обработка всех студентов из ответа:
		- Обнаружение новых оценок
		- Сохранение в БД
		- Отправка уведомлений
		- Удаление обработанных из `unprocessed_students`
	- Повтор цикла для оставшихся студентов
4. Сбор статистики синхронизации

**Результат:** Все студенты обработаны, включая все подгруппы

**3.3 Обнаружение новых оценок**
- Загрузка существующих оценок из БД
- Сравнение по уникальным ключам (`lesson_id`, `user_id`, `subject_id`)
- Возврат только новых записей

**3.4 Режим ожидания оценок**
- Установка флага в Redis с TTL
- Scheduler отправляет задачу синхронизации каждые 5 минут
- Автоматическое отключение после истечения времени

**⚠️ ВАЖНО:** Модуль НЕ выполняет синхронизацию напрямую, а вызывается ТОЛЬКО из Celery tasks.

**Взаимодействие:**
- **Входящие:** Celery Workers (вместо Handlers/Scheduler)
- **Исходящие:** JournalParser, Database (Grade, Subject, SyncLog), NotificationService, Redis (кеш, метаданные)

**Когда вызывается:**
- Из Celery task при ручной команде `/sync`
- Из Celery task после успешной авторизации
- Из Celery task по расписанию (каждые 6 часов)
- Из Celery task в режиме ожидания (каждые 5 минут)

### 4. Модуль уведомлений (`NotificationService`)

**Ответственность:** Отправка уведомлений пользователям

**Ключевые операции:**

**4.1 Уведомление о новых оценках**
- Проверка настроек пользователя 
- Проверка текущего времени (22:00 - 08:00 = ночь)
- Если ночь и `morning_notification_enabled = true`:
    - Вычисление времени до `morning_notification_time`
    - Отправка задачи `send_delayed_notification_task` с `eta` (absolute time)
	- **Групповое уведомление:** При наличии нескольких оценок в режиме ожидания формируется единое сообщение со списком (дата, предмет, оценка)
- Если день → немедленная отправка через Bot API
- Форматирование сообщения (предмет, дата, значение, средний балл)

**4.2 Месячный дайджест**
- Сбор статистики за месяц
- Генерация таблицы с оценками по неделям
- Анализ успеваемости (тренд, средний балл, динамика)
- Формирование мотивационного сообщения
- Отправка с inline-кнопками ("Детали", "Экспорт")

**4.3 Форматирование уведомлений**
- Минималистичный формат
- Emoji для визуального разделения
- Краткие, но информативные сообщения

**⚠️ ВАЖНО:** Отложенные уведомления отправляются через Celery task с countdown.

**Взаимодействие:**
- **Входящие:** Celery Workers
- **Исходящие:** Bot API, Celery (отложенные уведомления), Database (настройки пользователя), Analytics

### 6. Модуль Workers (`CeleryWorkers`)

**Ответственность:** Выполнение тяжёлых фоновых задач

**Задачи:**

#### Высокий приоритет (priority=9):

**`sync_user_manual_task(user_id)`**
- Ручная синхронизация по команде `/sync`
- Вызывает `GradeSyncService.sync_user_grades(user_id)`
- Отправляет результат пользователю через Bot API
- Оппортунистическая синхронизация
- Retry: до 3 попыток при ошибках

**`sync_user_after_login_task(user_id)`**
- Первая синхронизация после авторизации
- Аналогично ручной

#### Средний приоритет (priority=5):

**`sync_watch_mode_users_task()`**
- Получение списка пользователей в режиме ожидания из БД (where `watch_mode_expires_at` > now()) 
- Синхронизация каждого через `GradeSyncService.sync_user_grades()` 
- Отправка уведомлений при новых оценках 
- Группировка ночных уведомлений (если включен режим "Откладывать до утра") 
- Обновление `watch_mode_last_sync_at` для предотвращения спама

**`send_delayed_notification_task(user_id, grade_data)`**
- Отложенное уведомление о новой оценке
- Отправляется с eta=morning_time (абсолютное время) 
- Отправка задачи `send_night_accumulated_notifications_task` в Celery 
- Получение всех накопленных ночных уведомлений из Redis 
- Группировка по пользователям 
- Отправка одного сообщения со всеми оценками за ночь 
- Очистка очереди в Redis

#### Низкий приоритет (priority=1):

**`sync_all_users_task()`**
- Автоматическая фоновая синхронизация (каждые 6 часов)
- Вызывает `GradeSyncService.sync_all_users()`
- Группировка по group_id
- Итеративная обработка подгрупп
- Отправка метрик в Prometheus

**`send_monthly_digests_task()`**
- Отправка месячных дайджестов (31 число, 12:00)
- Получение пользователей с `monthly_digest_enabled=True`
- Генерация отчётов через `StatisticsService`
- Отправка через `NotificationService`

**`cleanup_old_logs_task()`**
- Удаление логов синхронизаций старше 30 дней
- Выполняется каждые 2 дня в 3:00

**`collect_metrics_task()`**
- Сбор статистики использования бота
- Производительность синхронизации
- Отправка в Prometheus (каждый час)

**`cleanup_expired_watch_mode_task()`**
- Удаление записей `watch_mode_expires_at` < now()
- Очистка Redis ключей режима ожидания

**Настройки:**
- **Retry:** До 3 попыток с экспоненциальным backoff (1 мин → 2 мин → 4 мин)
- **Timeout:** 300 секунд на задачу
- **Concurrency:** 4 worker процесса (масштабируется)

**Взаимодействие:**
- **Входящие:** Celery broker (Redis)
- **Исходящие:** GradeSyncService, NotificationService, Database, Prometheus

**Ключевые операции:**

**7.1 Расчёт среднего балла**

**Взаимодействие:**

## Очереди задач (Celery)

### Архитектура

```
┌──────────────────────────────────────────┐
│      Telegram Bot Process                │
│      (ВСЕГДА отзывчив < 100ms)           │
└──────────────────────────────────────────┘
          ↓ (отправка задач)
┌──────────────────────────────────────────┐
│      Redis Broker                        │
│      queue: celery (default)             │
│      - Персистентность задач             │
│      - Приоритизация                     │
└──────────────────────────────────────────┘
          ↓ (забирают задачи)
┌──────────────────────────────────────────┐
│      Celery Workers (1-N процессов)      │
│      Worker 1: priority=9 (ручные)       │
│      Worker 2: priority=5 (средние)      │
│      Worker 3: priority=1 (фоновые)      │
│      Worker 4: async processing          │
└──────────────────────────────────────────┘
          ↓ (выполнение)
┌──────────────────────────────────────────┐
│      GradeSyncService, Notification,     │
│      Database, edu-tpi API               │
└──────────────────────────────────────────┘
```


### Конфигурация Celery

**Основные параметры:**
- **Приложение:** `journal_bot`
- **Broker:** Redis (база 1) - очередь задач
- **Backend:** Redis (база 2) - результаты выполнения
- **Сериализация:** JSON
- **Часовой пояс:** Europe/Moscow
- **Task acknowledgement:** Late (после выполнения)
- **Worker prefetch:** 1 задача за раз
- **Timeout:** 300 секунд (5 минут) на задачу
- **Soft timeout:** 270 секунд (предупреждение)

### Типы задач

#### 1. Синхронизация

**Ручная синхронизация (высокий приоритет):**
- **Задача:** `sync_user_manual_task(user_id)`
- **Приоритет:** 9 (высокий)
- **Процесс:**
    1. Вызов `GradeSyncService.sync_user_grades(user_id)`
    2. Сбор результатов синхронизации
	3. Оппортунистическая синхронизация
    4. Отправка уведомления пользователям через Bot API
- **Retry:** До 3 попыток с экспоненциальным backoff
**Когда:** По команде `/sync` от пользователя

**Автоматическая синхронизация (низкий приоритет):**
- **Задача:** `sync_all_users_task()`
- **Приоритет:** 1 (низкий)
- **Процесс:**
    1. Группировка пользователей по `group_id`
    2. Для каждой группы:
        - Получение токена
        - Запрос списка журналов
        - Итеративная обработка подгрупп через `unprocessed_students`
    3. Сбор статистики и отправка в Prometheus
**Когда:** Каждые 6 часов по расписанию

**Режим ожидания (средний приоритет):**
- **Задача:** `sync_watch_mode_users_task()`
- **Приоритет:** 5 (средний)
- **Процесс:**
    1. Получение списка `user_ids` из Redis (`watch_mode:users`)
    2. Для каждого пользователя алгоритм, как и в ручной синхронизации
    3. Удаление из Redis по истечении TTL
**Когда:** Каждые 5 минут

#### 2. Уведомления

**Отложенное уведомление:**
- **Задача:** `send_delayed_notification_task(user_id, grade_data)`
- **Приоритет:** 5 (средний)
- **Процесс:**
    - Отправка уведомления с задержкой (`countdown`)
    - Вызов `NotificationService.send_grade_notification()`
- **Особенность:** Выполняется через заданное время (например, 30 минут)

**Месячные дайджесты:**
- **Задача:** `send_monthly_digests_task()`
- **Приоритет:** 1 (низкий)
- **Процесс:**
    1. Получение пользователей с `monthly_digest_enabled=True`
    2. Генерация отчёта через `StatisticsService`
    3. Форматирование дайджеста
    4. Отправка через Bot API с кнопками
**Когда:** 31 число каждого месяца, 12:00

#### 3. Служебные задачи

**Очистка логов:**
- **Задача:** `cleanup_old_logs_task()`
- **Приоритет:** 1 (низкий)
- **Процесс:** Удаление логов старше 30 дней из таблицы `sync_logs`
**Когда:** Каждые 2 дня в 3:00

**Сбор метрик:**
- **Задача:** `collect_metrics_task()`
- **Приоритет:** 1 (низкий)
- **Процесс:**
    - Сбор статистики: активные пользователи, количество синхронизаций, средняя длительность, процент ошибок
    - Отправка в Prometheus
**Когда:** Каждый час

### Приоритезация задач

| Приоритет       | Задачи                                                                                                      | Обоснование                                   | Время выполнения          |
| --------------- | ----------------------------------------------------------------------------------------------------------- | --------------------------------------------- | ------------------------- |
| **9** (Высокий) | `sync_user_manual_task`, `sync_user_after_login_task`                                                       | Пользователь ждёт результата, критично для UX | Моментально               |
| **5** (Средний) | `sync_watch_mode_users_task`, `send_delayed_notification_task`, `send_night_accumulated_notifications_task` | Важно, но терпимо к задержкам до 1-2 минут    | Через 1-2 мин             |
| **1** (Низкий)  | `sync_all_users_task`, `send_monthly_digests_task`, `cleanup_old_logs_task`                                 | Фоновые операции, могут подождать             | Когда освободятся workers |

### Retry стратегия

**Параметры повтора:**
- **Максимум попыток:** 3
- **Начальная задержка:** 60 секунд
- **Экспоненциальный backoff:** Да (60с → 120с → 240с)
- **Максимальная задержка между попытками:** 600 секунд (10 минут)

**Типы ошибок:**
- **Временные** (`TemporaryError`) - повтор с увеличивающейся задержкой
- **Постоянные** (`PermanentError`) - немедленная отправка уведомления об ошибке пользователю, без retry

### Мониторинг

#### Экспорт метрик в Prometheus:

Используется библиотека `celery-prometheus-exporter` для передачи метрик Celery в Prometheus.

**Доступные метрики:**
```
# Размер очереди задач
celery_queue_length{queue="celery"} 150

# Активные задачи на worker
celery_active_tasks{worker="worker1"} 2

# Время выполнения задач
celery_task_duration_seconds{task="sync_user_manual_task",state="success"} 5.2

# Общее количество выполненных задач
celery_tasks_completed_total{task="sync_all_users_task"} 1234

# Количество ошибок
celery_task_failures_total{task="sync_user_manual_task"} 3

# Загрузка workers (%)
celery_worker_utilization_percent{worker="worker1"} 75

# Задачи в состоянии retry
celery_tasks_retrying_total{task="sync_user_manual_task"} 5

```


**Визуализация в Grafana:**
Создаётся отдельный дашборд **"Celery Performance"** с панелями:
1. **Очередь задач** - график размера очереди в реальном времени
2. **Throughput** - количество обработанных задач/минуту
3. **Среднее время выполнения** - по типам задач (высокий/средний/низкий приоритет)
4. **Worker utilization** - загрузка каждого worker процесса
5. **Failure rate** - процент ошибок по задачам
6. **Retry статистика** - количество повторных попыток

**Алерты:**
Настраиваются в Prometheus Alertmanager:
- `celery_queue_length > 1000` → масштабировать workers
- `celery_worker_utilization_percent > 90` → добавить workers
- `celery_task_failures_total > 10/hour` → проверить логи
- `celery_active_tasks == 0 for 5 minutes` → рестарт workers

**Преимущества:**
- Единая точка мониторинга (Grafana) для всех компонентов системы
- Исторические данные хранятся в Prometheus
- Автоматические алерты при проблемах
- Корреляция метрик Celery с метриками бота и БД

## Сценарии взаимодействия

### Сценарий 1: Авторизация пользователя

**Триггер:** Команда `/login`

**Последовательность:**

```
1. Handler получает команду /login
   ↓
2. Handler запрашивает учётные данные через FSM
   ↓
3. Пользователь вводит логин и пароль
   ↓
4. Handler → AuthService.authenticate_user(login, password)
   ↓
5. AuthService → JournalAPIClient.get_fingerprint()
   ↓
6. JournalAPIClient запрашивает GET /UserInfo/Devices/RandomIdentity
   ↓
7. Получен randomIdentity
   ↓
8. JournalAPIClient отправляет POST /tokenauth с логином, паролем и fingerprint
   ↓
9. Получен accessToken, expiresIn, id
   ↓
10. JournalAPIClient запрашивает GET /tokenauth для получения полной информации
   ↓
11. Получены: userID, groupID, group, fio
   ↓
12. AuthService → EncryptionService.encrypt(username, password)
   ↓
13. AuthService → Database.save_user(credentials, edu_user_id, group_id, group_name, fio)
   ↓
14. AuthService → Redis.set_token(user_id, token, TTL=30min)
   ↓
15. Handler → sync_user_after_login_task.apply_async(
       args=[user_id],
       priority=9
   )
   (задача отправлена в Celery, НЕ блокирует бота)
   ↓
16. Handler СРАЗУ отправляет сообщение:
    "✅ Авторизация успешна! Синхронизация запущена..."
    (БОТ ОТВЕТИЛ < 100ms)
   ↓
17. Celery Worker забирает задачу из очереди
   ↓
18. Worker → GradeSyncService.sync_user_grades(user_id)
   ↓
19. Процесс синхронизации выполняется в фоне (пару секунд)
   ↓

   ↓

## Работа с подгруппами

### Проблема

API edu-tpi возвращает в `journalData` **не всю группу**, а только **подгруппу студента**, если дисциплина делится на подгруппы (флаг `isSubGroup: true`).

**Пример:**
- Группа 584 ис-3: 25 студентов
- Дисциплина "Физкультура" делится на 2 подгруппы
- Подгруппа А: студенты 1-13
- Подгруппа Б: студенты 14-25

**Что возвращает API:**
- Запрос от студента подгруппы А → получаем только оценки подгруппы А
- Запрос от студента подгруппы Б → получаем только оценки подгруппы Б

### Решение

**Стратегия кеширования с учётом подгрупп:**

1. **Проверка наличия студента в кэше:**
   - Пытаемся получить данные из кеша `journal:{group_id}:{journal_id}:full`
   - Проверяем: есть ли `student_id` в списке `student_ids` кеша?
   - Если ДА → используем кэш
   - Если НЕТ → запрашиваем журнал

2. **Определение типа кеша:**
   - После запроса журнала проверяем флаг `isSubGroup`
   - Если `false` → кешируем с ключом `journal:{group_id}:{journal_id}:full`
   - Если `true` → кешируем с ключом `journal:{group_id}:{journal_id}:sub:{hash}`
     - `{hash}` = первые 8 символов MD5 от списка student_ids

3. **Сохранение списка студентов:**
   - В кэш добавляется поле `student_ids` со списком ID студентов
   - Используется для быстрой проверки наличия студента

### Алгоритм

```
Функция: get_journal_with_subgroup_support(group_id, journal_id, student_id)

1. Проверить кеш: journal:{group_id}:{journal_id}:full
   
2. Если кеш найден:
   2.1. Проверить: student_id в cached.student_ids?
   2.2. Если ДА → вернуть cached.grades[student_id]
   2.3. Если НЕТ → перейти к шагу 3

3. Запросить журнал через API
   
4. Распарсить оценки всех студентов из journalData

5. Получить список student_ids из распарсенных данных

6. Проверить флаг isSubGroup из ответа API

7. Определить ключ кеша:
   - Если isSubGroup = false:
     cache_key = "journal:{group_id}:{journal_id}:full"
   - Если isSubGroup = true:
     hash = MD5(sorted(student_ids))[:8]
     cache_key = "journal:{group_id}:{journal_id}:sub:{hash}"

8. Сохранить в Redis:
   {
     "is_subgroup": isSubGroup,
     "last_sync": timestamp,
     "journal_name": название,
     "student_ids": [список ID],
     "grades": {словарь оценок}
   }

9. Вернуть grades[student_id]
```

### Эффективность

| Ситуация | Запросов к API | Комментарий |
|----------|---------------|-------------|
| Журнал БЕЗ подгрупп (25 студентов) | **1** | Кешируется для всей группы |
| Журнал С подгруппами (2 подгруппы по 13 и 12) | **2** | По одному на подгруппу |
| Журнал С подгруппами (3 подгруппы) | **3** | По одному на подгруппу |

**Вывод:** В любом случае намного эффективнее, чем делать запрос для каждого студента (было бы 25 запросов).

## Производительность и масштабирование

### Текущие показатели (100 пользователей/день)

**С Celery:**
- **Время ответа бота:** **< 100ms** (всегда, любая команда)
- **Время синхронизации пользователя:** 5 секунд (в фоне, не блокирует)
- **Нагрузка на API edu-tpi:** ~100 запросов/день (групповое кеширование)
- **Снижение нагрузки:** 96% (было бы 2500 запросов без кеширования)
- **Бот НЕ блокируется:** никогда, даже во время массовой синхронизации

**Требования к инфраструктуре:**
- **VPS:** 2 CPU, 4GB RAM (с учётом Celery workers)
- **PostgreSQL:** Стандартная конфигурация, PGBouncer для connection pooling
- **Redis:** 512MB памяти (256MB кеш + 256MB broker)
- **Celery Workers:** 4 процесса (можно масштабировать до 16+)

### Узкие места

1. **Скорость ответа edu-tpi API**
   - Решение: Агрессивное кеширование (TTL = 1 час для журналов)
   - Retry с экспоненциальным backoff при ошибках

2. **Синхронизация большого количества пользователей**
   - Решение: Celery workers обрабатывают параллельно, группировка по group_id

3. **Генерация Excel файлов**
   - Решение: Генерация через Celery task для файлов > 1MB

### Преимущества Celery

1. **Отзывчивость:** Бот ВСЕГДА отвечает мгновенно (< 100ms)
2. **Масштабируемость:** Легко добавить workers → увеличить throughput
3. **Приоритизация:** Ручные операции выполняются первыми
4. **Retry механизмы:** Автоматический повтор при ошибках
5. **Мониторинг:** Flower для визуализации, Prometheus для метрик
6. **Персистентность:** Задачи сохраняются в Redis, не теряются при перезапуске

### Планы масштабирования (>500 пользователей)

   - Количество команд/минуту
   - Активные пользователи

2. **Celery Performance:**
   - Размер очереди задач
   - Throughput (задач/минуту)
   - Среднее время выполнения
   - Worker utilization

3. **Sync Performance:**
   - Количество синхронизаций/час
   - Среднее время синхронизации
   - Количество найденных новых оценок
   - Error rate

**Алерты:**
- **Критичные:**
  - Очередь задач > 1000 → масштабировать workers
  - Все workers down → рестарт сервиса
  - Время ответа бота > 500ms → проверить нагрузку
  
- **Важные:**
  - Task failure rate > 5% → проверить логи
  - Worker down > 5 минут → автоматический рестарт
  - Redis память > 90% → увеличить лимит

- **Информационные:**
  - Недоступность edu-tpi API > 5 минут → уведомление админа
  - Высокая нагрузка на БД (CPU > 80%) → проверить запросы

## Безопасность

### Защита учётных данных

1. **Шифрование данных:**
   - Алгоритм: Fernet (симметричное шифрование)
   - Шифруются: `edu_username`, `edu_password`
   - Ключ хранится в переменной окружения `ENCRYPTION_KEY`
   - Ротация ключа: процедура для обновления без потери данных

2. **Хранение токенов:**
   - JWT токены в Redis с коротким TTL (30 минут)
   - Автоматическое удаление при logout
   - Не хранятся в PostgreSQL

3. **Rate limiting:**
   - Middleware для ограничения количества запросов от пользователя
   - Защита от злоупотреблений и DDoS
   - Лимит: 30 команд/минуту на пользователя

### Валидация данных

- Все входные данные валидируются через Pydantic модели
- Санитизация перед отображением в Telegram
- Защита от SQL injection через ORM (SQLAlchemy)

### Логирование и аудит

- Все действия пользователей логируются
- Критические операции (login, logout, изменение настроек) записываются в audit log
- Интеграция с Sentry для отслеживания ошибок
- Celery tasks логируются с полным traceback при ошибках

### Ключевые архитектурные решения

1. **Celery для фоновых задач** - бот ВСЕГДА отзывчив, никогда не блокируется
2. **Групповое кеширование журналов** - снижение нагрузки на edu-tpi API в 25 раз
3. **Приоритизация задач** - ручные операции выполняются первыми
4. **Агрегированный вывод данных** - пользователь видит всю информацию сразу
5. **Оппортунистическая синхронизация** - обновление данных всех студентов из журнала
6. **Учёт подгрупп** - итеративная обработка до полной синхронизации
7. **Минимализм хранения** - сохраняем только необходимое, остальное вычисляем
