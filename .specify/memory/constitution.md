# Конституция Journal Bot

Проект: Telegram-бот электронного журнала edu-tpi (`C:\Users\User\Projects\journal_bot`).
Документ выведен из [ROADMAP.md](../../docs/ROADMAP.md) §12, [ARCHITECTURE.md](../../docs/ARCHITECTURE.md)
и правил работы агента. Конституция выше отдельных планов фаз: при конфликте побеждает она.

## Основные принципы

### I. Слои и единственный шлюз к внешнему миру

Код делится на слои: `handlers` → `services` → `integrations`/`database`. Обработчик
(`bot/handlers/**`) НЕ обращается к сети, БД или Redis напрямую — только через сервис.
Весь HTTP к edu-tpi идёт через `bot/integrations/edu_tpi.py`; парсинг ответов — там же,
не в сервисах и не в хендлерах. Синхронизация оценок — только `GradeSyncService`.

*Зачем:* edu-tpi нестабилен и меняет контракты; единственная точка отказа должна быть
единственной и покрытой тестами.

### II. Тест — условие закрытия, а не украшение

Новая бизнес-логика (парсер, диф оценок, политика уведомлений, статистика, экспорт)
поставляется вместе с тестом. Задача не закрывается, пока `pytest` не зелёный.
Тест пишется на поведение и граничные случаи (нет оценок, только пропуски, пустой журнал
чужой подгруппы), а не на реализацию. Внешние вызовы в тестах заменяются стабами из
`tests/fakes.py`, не живой сетью.

*Зачем:* 282 теста — единственное, что реально держит регресс в проекте без ревьюера.

### III. Конфигурация, а не константы

Любое значение, которое может измениться (лимиты, интервалы, таймауты, размеры, флаги),
живёт в `Settings` (`bot/core/config.py`, pydantic-settings) и `.env.example`, а не числом
в коде. Секреты (токен бота, `ENCRYPTION_KEY`, пароли БД и Redis) — только в `.env`;
`.env` в git не попадает. Пароли и токены пользователей не пишутся в логи, Sentry и метрики.

*Зачем:* прод и dev отличаются только `.env`; утечка секрета в лог — инцидент, а не баг.

### IV. Долгая операция — только задача Celery

Хендлер не выполняет синхронизацию, рассылку или экспорт синхронно: он ставит задачу
(`.delay`) и отвечает пользователю сразу. Задачи идемпотентны и берут блокировку, чтобы
двойной клик не порождал два прохода. Очереди — `sync`, `notify`, `maintenance`;
новые задачи наследуют `BaseTask` (ретраи, логи, метрики).

*Зачем:* Telegram ждёт ответа секунды, edu-tpi отвечает десятками секунд; блокировка
event loop'а = отвал всех пользователей.

### V. Локализация обязательна

Все пользовательские строки — через `_()`/`n_()` из gettext. Новая строка появляется
сразу в обеих локалях (`ru`, `en`), `.po` обновляется в том же коммите. Русский текст —
основной, английский — полноценный перевод, не заглушка.

*Зачем:* бот двуязычный по факту; полупереведённый экран — это баг интерфейса.

### VI. Схема БД меняется только миграцией

Любое изменение схемы — Alembic-миграция с рабочим `downgrade`, проверенная
`upgrade head` → `downgrade -1` → `upgrade head` на PostgreSQL 14. Модели SQLAlchemy
и миграции не расходятся. Данные пользователей не удаляются деструктивными операциями
без явного решения.

*Зачем:* продовая БД одна и без реплик; откат — единственная страховка.

### VII. Наблюдаемость без шума

Новые фоновые операции и внешние вызовы получают метрику (счётчик/гистограмму) и
структурный лог; ошибки, требующие вмешательства, — событие Sentry. В логах есть
`user_id`, но нет ФИО, пароля, токена и тела ответа edu-tpi. Существующие метрики
(`sync_*`, `notifications_*`, `celery_*`) не переименовываются без миграции дашбордов.

*Зачем:* без метрик «синхронизация молча не работает» обнаруживается через жалобу
пользователя, а не через алерт.

## Технологические рамки

- Python 3.11–3.13 (`requires-python = ">=3.11,<4.0"`), aiogram 3.32, SQLAlchemy 2.x async,
  PostgreSQL 14, Redis 7 (клиент `redis` 8.x), Celery 5.x, Docker Compose.
- Линтеры и типы — обязательны: `ruff` (`lint.select = ["ALL"]`, строгий), `ruff format`,
  `mypy bot/`; pre-commit обязателен. Подавление правила — только точечно и с комментарием,
  объясняющим причину.
- Windows — рабочая среда разработки. Сеть до PyPI и GitHub идёт через локальный прокси
  (`HTTPS_PROXY=http://127.0.0.1:10809`); без него `uv add`/`uv lock` падают.
- Один токен бота = один поллер: второй `python -m bot` даёт `409 Conflict`.
- Рабочие данные лежат в docker-томах (`tgbot_postgres-data`, `tgbot_backups-data`):
  `docker compose down -v` запрещён.

## Процесс разработки и контроль качества

1. Работа идёт по фазам [ROADMAP.md](../../docs/ROADMAP.md); фаза начинается со спеки и
   плана, а не с кода.
2. Одна задача — один осмысленный коммит в Conventional Commits: `feat(sync): …`,
   `fix(auth): …`, `docs: …`, `test: …`.
3. Перед PR: `ruff check .`, `ruff format --check .`, `mypy bot/`, `pytest` — всё зелёное;
   CI (тесты, линтеры на 3.11/3.12/3.13, образ) зелёный.
4. Definition of Done задачи: код соответствует [ARCHITECTURE.md](../../docs/ARCHITECTURE.md);
   тест на новую логику; пользовательский сценарий проверен руками в Telegram; статус в
   `ROADMAP.md` обновлён; в задаче нет `TODO` без ссылки на номер задачи.
5. Пользовательские сценарии не считаются проверенными, пока не пройдены в реальном
   Telegram — тест и рендер строки из БД этого не заменяют.

## Управление

Конституция выше планов, промптов и привычек: расхождение с ней — дефект, а не мнение.
Поправка вносится отдельным PR с обоснованием и указанием затронутых фаз; сам PR обязан
проходить те же проверки, что и код. Версионирование семантическое: MAJOR — удаление или
переопределение принципа, MINOR — новый принцип или существенное расширение, PATCH —
уточнение формулировки. Текущая версия — в конце файла; история — в git. Соблюдение
проверяется на ревью каждого PR и при приёмке фазы.
