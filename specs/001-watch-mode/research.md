# Research: режим ожидания оценок

## 1. Где живёт состояние режима

- **Decision**: источник истины — PostgreSQL (`users.watch_mode_expires_at`,
  `users.watch_mode_last_sync_at`); Redis-множество `watch_mode:users` — только быстрый индекс
  для планировщика.
- **Rationale**: режим переживает перезапуск воркера, beat и Redis; выборка «кто ждёт» —
  один индексный запрос по `watch_mode_expires_at`. Обе колонки уже созданы миграцией
  `2025-12-14_update_models_according_to_requirements.py`, схему менять не нужно.
- **Alternatives**: ключ `watch_mode:<user_id>` с TTL — отклонено: ARCHITECTURE §4.2 прямо
  называет `watch_mode:users` единственным исключением без TTL, потому что TTL-ключ не даёт
  узнать «кто был в режиме» после истечения и расходится с БД при рестарте. Только Redis —
  отклонено: состояние теряется, пользователь остаётся «в режиме» без записей.

## 2. Расхождение индекса и БД

- **Decision**: цикл синхронизации читает **БД**, а не множество Redis; уборка сверяет
  множество с БД и восстанавливает его (`SADD` по актуальным, `SREM` по истёкшим).
- **Rationale**: если Redis очистили, режим продолжает работать, а индекс самовосстанавливается
  на следующем цикле уборки; «залипших» активных пользователей не возникает (SC-006).
- **Alternatives**: считать множество единственным источником — отклонено (см. п.1);
  сверять в каждом цикле (каждые 5 минут) — избыточно, часовая уборка дешевле и достаточна.

## 3. Продление: что именно значит «не более 30 минут подряд»

- **Decision (по умолчанию для плана)**: продление доступно, пока период активен, и даёт
  новый срок «сейчас + 30 минут». Слова «не более 30 минут подряд» из ARCHITECTURE §2
  трактуются как «без продления режим не дольше 30 минут».
- **Rationale**: предсказуемо для пользователя и не требует хранить накопленное время;
  продление — явное действие, случайно режим не продлевается.
- **Alternatives**: жёсткий потолок «30 минут суммарно, продление запрещено» — отклонено как
  основное, потому что ломает сценарий «преподаватель задерживается»; но это **открытое
  решение** для владельца продукта: если выберут потолок, меняется только проверка в
  `WatchModeService.extend` и один тест. Зафиксировано в `checklists/requirements.md`.
- **Что не меняется при любом выборе**: проверки идут каждые 5 минут, число запросов к журналу
  не зависит от числа продлений.

## 4. Как запускается проверка

- **Decision**: `beat_schedule` в `bot/celery_app.py`: `sync-watch-mode-users` —
  `crontab(minute="*/5")`, `cleanup-expired-watch-mode` — `crontab(minute=10)` (ARCHITECTURE §6.6),
  обе задачи в очереди `sync` (уборка — в `maintenance`), `expires=240` у пятиминутной задачи,
  чтобы отставший воркер не выполнял устаревший цикл.
- **Rationale**: ровно одна задача на цикл, независимо от числа пользователей; не нужны
  `eta`-задачи на каждого пользователя; `expires` защищает от «пачки догоняющих циклов».
- **Alternatives**: `countdown`-задача на пользователя с цепочкой self-retry — отклонено:
  N пользователей = N задач, шум в брокере и сложнее тестировать.

## 5. Синхронизация: новый сервис или существующий

- **Decision**: переиспользуем `GradeSyncService.sync_user` для каждого ожидающего; новый
  код — только оркестрация выборки, метрик и уведомлений.
- **Rationale**: групповой кеш журналов (`journal_cache`, ключи `journal:*`) уже общий для
  пользователей одной группы, поэтому второй студент той же группы не порождает второго
  запроса к edu-tpi (SC-005). Диф оценок, `sync_logs`, upsert — уже проверены 282 тестами.
- **Alternatives**: отдельный «лёгкий» клиент для режима — отклонено: дублирование логики
  авторизации/401/кеша; вызов `GroupSyncService.sync_all()` — отклонено: обошёл бы всех
  пользователей, а не только ожидающих.
- **Открытый технический риск**: `sync_user` пишет `sync_logs` с типом `manual`. Нужен
  параметр `sync_type=SyncType.WATCH_MODE`, иначе история врёт (FR-012). Проверяется тестом.

## 6. Уведомления в режиме

- **Decision**: после `sync_user` новые оценки уходят через
  `send_grade_notification.delay(..., immediate=True)` — тот же путь, что у ручной
  синхронизации, с обходом политики «накопить до утра»: в режиме ожидания пользователь ждёт
  оценку сейчас, в том числе ночью.
- **Rationale**: политика «день/ночь», ночная очередь и дедупликация уже реализованы и
  покрыты тестами (фаза 3); режим не вводит новый вид уведомлений (FR-008, SC-003).
- **Alternatives**: слать своё «ускоренное» сообщение — отклонено: дубли и второй набор
  текстов, расхождение с `/settings`. Оставить ночную политику — отклонено после обсуждения:
  «проверять каждые 5 минут» и «покажу утром» противоречат друг другу.

## 7. Индикатор в интерфейсе

- **Decision**: индикатор — на экране режима (остаток времени) и в подтверждающем сообщении;
  кнопка главного меню не меняется.
- **Rationale**: меню рендерится на каждое открытие и не должно ходить в БД за состоянием
  режима (лишний запрос на каждое действие). Пользователь видит статус там, где он про него
  спрашивает.
- **Alternatives**: «глаз»/таймер в тексте главного меню — возможно позже, отдельной задачей,
  если будет запрос от пользователей.

## 8. Время в тестах

- **Decision**: в `bot/services/watch.py` — локальная функция `now()` (как в
  `bot/services/notifications.py`), тесты подменяют её через monkeypatch.
- **Rationale**: новая зависимость (`freezegun`/`time-machine`) не нужна, приём в проекте
  уже используется; тесты остаются быстрыми и без глобального патчинга `datetime`.
- **Alternatives**: `freezegun` — отклонено ради одной фичи; инъекция `clock` в конструктор —
  избыточно для двух функций.

## 9. Идемпотентность и гонки

- **Decision**: включение/продление — один `UPDATE … SET watch_mode_expires_at = :t` с
  последующим `SADD`; выключение — `SET NULL` + `SREM`; цикл синхронизации дополнительно
  берёт существующий member-lock (`GradeSyncService._member_lock`), чтобы ручная и
  watch-синхронизация одного пользователя не шли одновременно.
- **Rationale**: два нажатия подряд не создают второго «режима», а двойной цикл не порождает
  двойных уведомлений (дедупликация всё равно страхует).
- **Alternatives**: распределённый lock на весь цикл — отклонено: не нужен, цикл и так один
  на beat-интервал, а `expires` отсекает дубли.

## 10. Поведение без авторизации

- **Decision**: `WatchModeService.enable` требует `is_authenticated` и действующий токен;
  иначе возвращает причину отказа, хендлер отвечает «сначала войдите» и состояние не меняет.
- **Rationale**: FR-013; без токена цикл всё равно не сможет прочитать журнал и только
  засорит историю ошибками.
- **Alternatives**: разрешать и молча ничего не делать — отклонено: пользователь думает, что
  режим работает.
